OutRay has four products in one organization workspace. Start with the product that matches your task; you do not need a tunnel to use Observability, Secrets, or Uptime.

<Cards>
  <Card title="Tunnels" href="/docs/tunnels">

  </Card>
  <Card title="Observability" href="/docs/observability">

  </Card>
  <Card title="Secrets" href="/docs/secrets">

  </Card>

## Start with a task

- [Share a local server](/docs/opening-a-tunnel): install the CLI and run `outray http 3000`.
- [Connect application telemetry](/docs/observability/getting-started): create a **Send telemetry** token and initialize a server SDK.
- [Run an app with managed secrets](/docs/secrets/getting-started): create a vault, select an environment, and run `outray secrets run -- npm run dev`.
- [Monitor a public endpoint](/docs/uptime/getting-started): create an HTTP check before choosing what becomes public.

## Shared workspace

[Organizations and membership](/docs/platform/organizations) determine who can see and manage workspace resources. [API tokens](/docs/platform/api-tokens) give machine clients explicit permissions. [Agent](/docs/platform/agent) can investigate observability evidence without changing your application or workspace.

Keep machine credentials and exported secret values out of browser bundles, source control, and screenshots. The guides use placeholders and server-side configuration; replace them in your own secret provider.

## How the products fit together

A development workflow can use a tunnel for incoming webhooks, Observability to inspect the handler, and Secrets to supply its credentials. Uptime separately probes a public endpoint and can feed a status-page component. Telemetry health, monitor state, and public incident publication are different kinds of evidence—not interchangeable claims that a service is healthy.

The existing [tunnel CLI reference](/docs/cli-reference), [protocol guide](/docs/protocols), SDKs, and framework integrations remain available in the navigation.
